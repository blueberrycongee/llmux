# 融合路由记忆与候选模型调度的异构大模型网关研究与实现

> 英文题目：Research and Implementation of a Heterogeneous LLM Gateway Integrating Route Memory and Candidate Model Scheduling

## 摘要

随着大语言模型应用逐步从单模型调用走向多角色、多任务、多后端协同，传统“业务系统直接对接模型服务”的模式在接口适配、治理控制、路径选择与运行稳定性方面暴露出明显不足。尤其在 Agent 场景下，请求不仅具有任务语义差异，还同时受到历史上下文、路由经验、模型能力边界、限流约束、工具可用性和运行态负载等多因素影响。因此，如何在统一网关中同时处理 Agent 级路由、团队级协作与模型级调度，成为异构大模型基础设施中的关键问题。

针对上述问题，本文围绕异构大模型网关中的多层决策过程开展研究，提出了一种融合 Route Memory、Team Memory 与候选模型调度的异构网关方案。该方案将路由过程划分为三个层次：第一层根据请求语义、Team Registry、历史 Team Memory 与复杂度特征进行 Expert Agent Team 选择；第二层在目标团队内部根据任务意图选择 lead Expert Agent，并结合 Agent Registry、Route Memory 与工具绑定信息完成角色路由；第三层在目标 Agent 绑定的候选模型池中，结合候选权重、运行态 RPM/TPM 使用量、cooldown 状态与预测压力进行主动调度，从而降低限流碰撞概率并提升请求执行成功率。与此同时，本文进一步将开源 MCP 工具接入网关，使 Expert Agent 不再只是由 system prompt 限定的静态角色，而是演进为具备真实工具调用能力的 Tool-Augmented Expert Agent。基于该思路，本文实现了一个可运行的异构大模型网关原型系统：后端采用 Go 实现统一协议接入、治理控制、团队/Agent 路由执行、工具注入与候选模型调度，前端采用 Next.js 实现管理台、Team/Agent Registry、Route Memory、Team Memory、团队演练与候选模型运行态可视化。

本文的主要工作包括：构建面向 Agent 场景的异构网关总体架构；设计 Team Memory 与 Route Memory 协同驱动的 Team/Agent 分层路由方法；设计支持候选模型池的预测式调度方法；设计 Expert Agent Team 演练与经验沉淀机制；完成开源 MCP 工具接入、多租户治理、审计与可观测支撑；并通过接口测试、联调测试和调度验证对方案进行初步分析。结果表明，本文方法能够在统一接入异构模型资源的同时，增强团队协作路由的可解释性、工具增强 Agent 的可执行性和候选模型选择的稳定性，为后续开展面向自适应团队路由、工具增强协作与模型增强调度的研究提供了原型基础。

**关键词**：异构大模型网关；Route Memory；Team Memory；Expert Agent Team；工具增强智能体；候选模型调度；预测式限流规避

## 第1章 绪论

### 1.1 研究背景

大语言模型正在成为新一代智能应用的基础能力，但实际部署环境中的模型资源并非单一、稳定、同构的后端，而是由不同供应商、不同能力边界、不同成本结构和不同限流条件构成的异构资源池。与此同时，Agent 系统的发展使上层请求不再只是统一的文本生成任务，而是逐步演化为规划、研究、写作、编码、工具调用等多类型任务混合场景。在这种背景下，请求分发问题已经从“把请求发给哪个模型”扩展为“根据任务语义、历史经验与运行状态，在多层次资源中如何做更合理的决策”。

现有工程实践中，很多系统通过统一协议或多 provider 适配实现模型接入，但更多关注“如何调用更多模型”，而非“如何更合理地路由这些请求”。当请求同时面临语义异构、任务异构、模型异构和运行时动态约束时，仅依赖固定规则或简单轮询策略往往难以满足 Agent 场景需求。因此，本文将研究重点放在异构大模型网关中的两级路由问题：即如何在 Agent 层和候选模型层分别完成合理决策，并使二者形成统一、可扩展、可治理的中间层体系。

### 1.2 研究意义

#### 1.2.1 理论意义

本文的理论意义主要体现在三个方面。首先，本文将异构大模型网关问题从单纯的协议兼容与请求转发扩展到 Agent 场景中的两级路由问题，使网关研究从工程中间层进一步延伸到任务语义驱动的资源调度层。其次，本文将 Route Memory 引入路由决策过程，强调历史路径与执行结果在后续相似请求中的辅助价值，从而为“记忆增强路由”提供具体原型。最后，本文提出将候选模型池的主动预测调度纳入网关体系，使模型选择不再只依赖静态权重或失败后切换，而是能够在请求发送前结合运行态压力提前规避高风险候选模型。

#### 1.2.2 实践意义

在工程实践层面，本文工作有助于降低上层 Agent 系统对底层模型差异的感知和耦合；提升统一网关在多租户、多模型、多任务场景下的治理能力；增强路由解释、运行观测与候选模型切换的可视化能力；并为后续实现更加复杂的自适应路由与智能调度奠定平台基础。

### 1.3 国内外研究现状

#### 1.3.1 国外研究现状

国外在模型统一接入、Agent 编排与平台化基础设施方面已形成较多实践。例如，LiteLLM、OpenRouter 等系统主要解决多模型统一接入与协议兼容问题，LangChain、LangGraph 等框架则主要关注上层工作流、工具调用和多 Agent 编排问题。但现有系统普遍偏重某一侧：要么强调模型接入，要么强调应用编排，较少在同一框架内同时讨论 Route Memory、候选模型池和运行态预测调度等问题。

#### 1.3.2 国内研究现状

国内近年来在大模型中台、模型服务平台和智能体平台方面发展较快，已经开始重视模型统一接入、权限控制、预算约束和平台治理。不过，从研究视角来看，国内已有工作大多仍停留在平台整合或业务应用层，较少围绕“面向 Agent 场景的异构路由问题”形成明确的问题建模与方法设计。尤其是将历史路由经验与候选模型预测式调度统一纳入网关体系的研究仍相对不足。

### 1.4 研究问题、研究内容与研究方法

#### 1.4.1 研究问题

本文围绕以下四个核心问题展开。

- **RQ1：** 在多 Agent 场景下，如何利用请求语义与历史 Route Memory 提升 Agent 路由的合理性与一致性？
- **RQ2：** 当复杂任务无法由单一 Agent 高质量完成时，如何在网关层引入 Expert Agent Team，并利用 Team Memory 提升团队级协作路由的复用能力？
- **RQ3：** 当同一 Expert Agent 绑定多个候选模型与多个外部工具时，如何结合运行态使用量、限流约束与工具绑定信息进行主动调度，而不是仅在失败后被动切换？
- **RQ4：** 如何将 Team 路由、Agent 路由、候选模型调度、工具增强执行与多租户治理整合为统一的异构大模型网关原型系统？

#### 1.4.2 研究内容

围绕上述问题，本文主要开展以下工作：

1. 设计面向 Agent 场景的异构大模型网关总体架构；
2. 构建基于 Team Registry、Agent Registry、Team Memory 与 Route Memory 的分层路由机制；
3. 构建支持候选模型池的主动预测调度机制；
4. 构建开源 MCP 工具接入与 Tool-Augmented Expert Agent 执行机制；
5. 设计 Expert Agent Team 演练与经验沉淀机制；
6. 完成多租户治理、审计与可观测支撑；
7. 完成系统原型实现并对团队路由、工具注入与候选模型调度进行验证。

#### 1.4.3 研究方法

本文综合采用文献研究法、问题建模法、原型实现法与实验验证法。首先通过相关研究梳理异构网关与 Agent 路由的发展现状；其次对 Agent 路由与候选模型调度问题进行抽象；然后基于 Go 与 Next.js 实现可运行原型；最后通过测试与案例验证分析方法有效性。

### 1.5 论文结构

全文共分六章。第一章介绍研究背景、研究问题和研究意义；第二章介绍相关理论与技术基础；第三章对面向 Agent 场景的异构路由问题进行建模；第四章提出融合 Route Memory 与候选模型调度的方法；第五章介绍系统实现与实验验证；第六章总结全文并展望未来工作。

## 第2章 相关理论与技术基础

### 2.1 核心理论基础

#### 2.1.1 网关与中间层理论

网关不仅承担统一入口功能，更重要的是承担协议收敛、治理控制、流量分发和运行观测职责。在大模型场景中，网关的价值在于把底层异构模型资源抽象为统一服务能力，并将路由与治理能力从业务系统中上收为平台能力。

#### 2.1.2 Agent 系统、团队协作与多层路由思想

Agent 并非单一模型调用实体，而是能够根据任务目标、工具能力和上下文状态执行不同动作的智能角色。在进一步的复杂任务场景中，单一 Agent 往往难以同时完成研究分析、结构规划、代码实现与结果表达等多类型子任务，因此有必要引入 Expert Agent Team，将多个具备不同专长的 Agent 组织为可复用的协作单元。在此基础上，面向 Agent 的网关需要解决三层路由问题：先确定是否应由 Expert Agent Team 处理请求，再确定由团队中的哪个 lead Agent 承担主执行角色，最后确定该 Agent 应由哪个底层候选模型执行。

#### 2.1.3 路由记忆思想

Route Memory 的核心思想是将历史 query、路径选择与执行结果沉淀为可复用知识，使后续相似请求能够参考历史高质量路径，从而提升路由稳定性与一致性。与普通日志不同，Route Memory 面向的是“后续决策可复用”的结构化经验。在团队协作场景中，这一思想还可进一步扩展为 Team Memory：即将历史任务、被选中的专家团队、团队参与成员与最终协作摘要沉淀为团队级经验，为复杂任务的团队路由与复用提供依据。

#### 2.1.4 工具增强 Agent 思想

在传统 Prompt-Based Agent 中，角色能力更多由 system prompt 描述，其“会做什么”主要停留在语言层面的能力声明。本文进一步引入 Model Context Protocol（MCP）工具接入机制，使 Agent 可绑定真实外部工具，并在请求执行过程中通过工具调用完成网页抓取、文件读写、浏览器自动化与仓库操作等任务。由此，Agent 从“基于提示词的角色代理”演进为“具备真实外部执行能力的工具增强智能体（Tool-Augmented Expert Agent）”。

#### 2.1.5 主动调度与限流规避思想

在异构模型场景中，模型选择不应只依赖静态权重或失败后切换机制。由于不同候选模型存在不同 RPM、TPM 与并发边界，若能在请求发送前结合近一分钟使用量和本轮请求预估负载进行主动判断，则有望减少限流碰撞，提高整体可用性。这构成了本文候选模型预测式调度方法的理论基础。

### 2.2 关键技术概述

本文系统以后端 Go 服务和前端 Next.js 管理台为主要实现载体，并结合 OpenAI 兼容协议、可选 Redis/数据库持久化能力以及 Prometheus、OpenTelemetry 等观测技术，构成完整的原型支撑环境。

## 第3章 面向 Agent 场景的异构路由问题建模

### 3.1 问题场景定义

本文研究的目标场景可描述为：系统外部存在一组用户请求，请求具有不同语义目标与复杂度水平；系统内部维护一组 Conversation Agent，每个 Agent 对应不同能力角色，并可进一步绑定一组真实外部工具；在 Agent 之上，系统还维护一组 Expert Agent Team，用于承接需要多角色协作的复杂任务；每个 Agent 下进一步绑定一个候选模型池，候选模型在能力、成本、延迟与限流边界上存在差异。网关的任务是在给定请求、历史 Route Memory、Team Memory 与运行态约束的条件下，做出尽可能合理的多层决策。

### 3.2 形式化要素

设用户请求集合为 \(Q\)，Agent 集合为 \(A\)，专家团队集合为 \(T\)，候选模型集合为 \(M\)，工具集合为 \(U\)。对于任意请求 \(q \in Q\)，第一阶段需要判断是否应由某个团队 \(t \in T\) 处理该请求；若命中团队，则第二阶段需要在团队参与成员中选择合适的 lead Agent \(a \in A\)；第三阶段则需要在该 Agent 对应的候选模型子集 \(M_a \subseteq M\) 中选择一个可执行候选模型 \(m\)。与此同时，Agent 的工具绑定集合 \(U_a \subseteq U\) 将影响该 Agent 的实际可执行能力边界。

其中，团队选择主要受请求复杂度、任务类型、历史 Team Memory 与协作模式描述影响；Agent 选择主要受请求语义、角色能力、历史 Route Memory 与工具绑定信息影响；候选模型选择主要受候选权重、当前使用量、RPM/TPM 约束、cooldown 状态和预测压力影响。

### 3.3 优化目标

本文不把问题严格建模为单一数值最优化问题，而是从工程可实现性出发，将目标概括为以下四项：

1. 提升团队路由与 Agent 路由的语义匹配合理性；
2. 提升相似请求在 Team Memory 与 Route Memory 层面的路径复用能力；
3. 降低候选模型限流碰撞概率；
4. 提升工具增强 Agent 在复杂任务场景中的实际可执行性；
5. 提升整体请求成功率、协作稳定性与路由可解释性。

### 3.4 设计挑战

该问题存在以下几个挑战：

1. 请求语义与团队能力、Agent 能力之间缺乏直接结构化映射；
2. Team Memory 与 Route Memory 需要兼顾历史经验复用与当前请求差异；
3. 候选模型运行状态与工具可用性均具有动态性；
4. 团队协作、工具注入与候选模型调度既要追求可用性，也要兼顾治理边界与实现复杂度。

## 第4章 融合 Route Memory 与候选模型调度的方法设计

### 4.1 总体方法框架

本文提出一种三层路由方法。第一阶段根据请求复杂度、任务语义、Team Registry 与 Team Memory 完成团队级路由；第二阶段在目标团队内部结合 Agent Registry、Route Memory 与工具绑定信息完成 lead Agent 路由；第三阶段在目标 Agent 的候选模型池中执行预测式调度。整体上形成“团队选择—Agent 选择—候选模型排序—执行与回写”的闭环流程。

### 4.2 基于 Team Memory 与 Route Memory 的分层路由方法

系统首先根据 query 的语义复杂度与显式协作信号判断是否需要进入团队级协作路径；对于命中的复杂任务，系统从 Team Registry 中检索候选 Expert Agent Team，并结合历史 Team Memory 识别与当前任务相近且 outcome score 较高的团队级经验，从而完成团队选择。随后，系统在被选中的团队内部，依据当前意图、成员角色能力、历史 Route Memory 与工具绑定情况，选择合适的 lead Agent 承担主执行角色。

该过程可同时包含 consulted memory 与 reused memory 两类：在团队层，consulted team memory 表示历史团队协作经验被参考但未直接复用，reused team memory 表示某条高分团队经验被直接复用于当前路径；在 Agent 层，consulted route memory 与 reused route memory 则继续承担单 Agent 路由的经验辅助作用。通过 Team Memory 与 Route Memory 的协同，系统能够在复杂任务中同时保留“团队级经验复用”和“角色级路径复用”两种能力。

### 4.3 工具增强 Expert Agent 与候选模型池的预测式调度方法

对于已经选中的 lead Expert Agent，系统进一步考虑两类执行增强信息：其一是该 Agent 所绑定的外部工具集合，其二是其候选模型池。首先，系统将平台工具市场中的条目解析为底层 MCP 工具，并按 Agent 的工具绑定关系注入到本轮请求上下文中，使模型能够在生成阶段按需触发真实工具调用。由此，Agent 的执行过程不再局限于语言生成，而是可以借助网页抓取、文件系统、浏览器自动化和仓库操作等能力增强任务完成质量。

在模型选择层，对于已经选中的 Expert Agent，系统进一步在其候选模型池中执行调度。每个候选模型包含 provider、model、weight、rpm_limit 和 tpm_limit 等信息。系统首先估算本轮请求 token 数，再读取候选模型近一分钟内的本地 usage 统计，得到 current_rpm 与 current_tpm。之后结合候选模型权重和预测压力计算 selection score，并据此排序候选模型。

若某候选模型在本轮请求执行后预测将超过 RPM 或 TPM 阈值，则直接标记为 predicted_saturated 并跳过；若候选模型处于 cooldown，则标记为 cooling_down 并跳过；否则优先选择 score 更高的候选模型执行。若执行阶段仍发生限流或故障，则进入 failover，切换至下一个候选模型。该方法实现了从“失败后切换”向“发送前规避高风险候选”的演进。

### 4.4 Expert Agent Team 演练与经验沉淀机制

为了提升团队级协作路径的可复用性，本文在网关原型中进一步设计了 Expert Agent Team Rehearsal 机制。该机制允许为某个团队显式发起一次 rehearsal 请求，使团队中的多个 Agent 以同一任务为输入分别给出分析结果，系统再将各成员输出摘要拼接为团队级 summary，并记录参与成员、任务内容、执行结果与 outcome score，沉淀为新的 Team Memory。这样，系统不仅能在真实对话流中被动积累团队经验，还能通过显式演练方式主动打磨团队配置与协作路径。

本文方法的特点主要体现在以下四个方面：

1. 通过 Team Memory 与 Route Memory 协同增强分层路由，使历史经验进入团队层与 Agent 层决策；
2. 通过工具市场与 MCP 工具注入机制增强 Expert Agent 的真实可执行能力；
3. 通过候选模型池预测式调度增强模型选择的主动性；
4. 将团队协作、工具增强执行、候选模型调度与治理边界统一纳入异构网关体系，而不是把这些逻辑散落在上层业务中。

## 第5章 系统实现与实验验证

### 5.1 系统实现概述

本文基于 Go 实现后端网关原型，完成统一协议接入、Conversation Agent 管理、Expert Agent Team 管理、Route Memory 记录、Team Memory 记录、多租户治理与候选模型调度；基于 Next.js 实现前端管理台，用于展示 Team Registry、Agent Registry、Route Memory、Team Memory、selected candidate、candidate failovers、candidate states 与团队演练结果等运行态信息。同时，系统还接入了基于 MCP 的工具执行链路，支持将开源工具源上架到工具市场，并进一步绑定给 Expert Agent 使用。系统实现的意义在于为本文提出的团队—Agent—候选模型三层路由方法提供可运行验证载体。

### 5.2 实验设计

本文实验主要围绕四个问题展开：

1. 系统是否能够根据 query 语义、复杂度与历史 Team/Route Memory 合理选择 Expert Agent Team 与 lead Agent；
2. 系统是否能够在团队演练接口中正确返回 selected_team、participating_agents、steps 与 recorded_memory 等关键字段；
3. 系统是否能够在同一 Agent 下正确返回 selected candidate、candidate failovers 与 candidate states；
4. 系统是否能够在候选模型接近 RPM/TPM 上限时，提前跳过 predicted_saturated 候选模型，从而降低限流碰撞风险。

### 5.3 结果分析

实验结果表明，系统能够在对话接口中正确返回 selected_team、team_participants、selected_agent、selected_candidate、candidate_failovers 和 candidate_states 等关键字段；能够在团队演练接口中正确返回 participating_agents、steps 与 recorded_memory；能够记录 consulted/reused route memory 与 team memory 情况；并能够在候选模型调度层基于近一分钟 usage 与预测压力计算 selection score，对高风险候选模型进行主动避让。同时，借助工具市场与 MCP 工具注入机制，Expert Agent 已具备真实外部工具调用能力，而不再只是由 system prompt 限定的静态角色。说明本文提出的团队—Agent—候选模型三层路由思路具备可实现性与初步有效性。

### 5.4 讨论

需要说明的是，本文当前验证仍以原型系统和功能性实验为主，尚未形成大规模统计对比实验。例如，候选模型 usage 当前主要保存在本地内存中，尚未实现多实例共享；调度 score 当前主要考虑 weight、RPM/TPM 压力与 cooldown 状态，尚未纳入更完整的 latency、cost 与 success rate 因子；团队协作当前主要采用“team 选择—lead agent 执行—rehearsal 经验沉淀”的轻量模式，尚未进一步扩展为更强的并行子任务分解与团队自治机制；工具增强能力当前已支持基于 MCP 的真实工具调用，但在权限隔离、工具质量评估与工具效果反馈方面仍有继续研究空间。因此，本文的贡献更适合作为“研究原型与方法验证”，而非最终成熟调度系统。

## 第6章 总结与展望

本文围绕异构大模型网关中的多层路由问题，提出并实现了一种融合 Route Memory、Team Memory 与候选模型调度的异构网关方案。研究表明，将历史团队经验引入 Team 路由层、将历史角色经验引入 Agent 路由层、将运行态预测调度引入候选模型层，并进一步引入工具增强 Expert Agent 机制，有助于提升路径选择的解释性、连续性、协作稳定性与实际执行能力。基于这一方法，本文实现了一个可运行原型系统，为后续研究面向自适应团队路由、工具增强协作与模型增强调度的异构网关提供了平台基础。

未来可从以下方向继续开展工作：一是将候选模型 usage 状态迁移至 Redis 等共享存储中，支持多实例协同调度；二是在调度中引入 latency、cost、success rate 等更多指标，形成综合评分方法；三是强化 Route Memory 与 Team Memory 的语义检索能力；四是进一步扩展 Expert Agent Team 的并行协作与角色协商机制；五是加强工具调用的权限治理与效果反馈闭环；六是进一步引入 LLM 增强调度器，使系统具备更强趋势预测与策略建议能力。
