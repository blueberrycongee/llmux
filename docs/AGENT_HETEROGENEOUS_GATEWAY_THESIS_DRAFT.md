# 毕设项目初稿：Agent 异构网关系统实现总结

## 1. 项目名称

Agent 异构网关系统设计与实现

可选英文名：Design and Implementation of an Agent-Oriented Heterogeneous LLM Gateway

---

## 2. 项目背景

随着大语言模型与智能体（Agent）系统的快速发展，越来越多的应用不再依赖单一模型或单一服务，而是需要在 OpenAI、Anthropic、Google、Azure OpenAI 以及各类兼容 OpenAI 协议的私有化模型服务之间灵活切换。同时，在真实业务场景中，还需要解决多租户访问控制、模型路由、限流、预算控制、日志审计、可观测性和可视化管理等问题。

更重要的是，Agent 系统天然具有明显的**异构性**。这种异构并不只体现在“底层模型供应商不同”，还体现在以下多个维度：

1. **模型异构**：不同厂商提供的模型接口、计费方式、能力边界和性能特征不同；
2. **协议异构**：虽然很多服务兼容 OpenAI 风格接口，但在参数、流式返回、错误语义和扩展字段上仍存在差异；
3. **能力异构**：有的模型更适合推理，有的更适合对话、嵌入、语音或低成本调用；
4. **部署异构**：模型可能来自公有云、私有部署、代理转发服务或本地推理节点；
5. **租户异构**：不同团队、用户、组织对应不同预算、权限、限流和审计要求；
6. **Agent 任务异构**：不同 Agent 在一个系统中承担规划、检索、协调、执行、评估等不同职责，对模型能力和稳定性的要求并不一致。

传统做法通常是：

1. 每个应用各自对接不同模型厂商；
2. 每个 Agent 系统单独实现鉴权、统计、预算和路由；
3. 管理界面与网关逻辑分离，缺乏统一治理能力；
4. 上层应用直接感知底层模型差异，导致系统耦合严重。

这种方式会导致系统复杂度高、维护成本大、复用性差，也不利于后期将多个智能体系统统一接入与治理。

因此，本项目尝试设计并实现一个**面向 Agent 场景的异构网关系统**：把多模型接入、协议屏蔽、路由调度、治理控制、运维观测和可视化沙盘能力统一到一个平台中，使上层 Agent 应用通过统一入口访问底层异构模型资源，并由网关负责适配、分发、治理和观测，为后续智能体编排、群体仿真和社会沙盘演练提供底层支撑。

---

## 3. 项目目标

本项目的主要目标包括：

- 实现一个兼容 OpenAI 风格接口的高性能网关；
- 支持多种异构模型提供方统一接入；
- 支持多种路由策略，实现模型请求的动态分发；
- 提供多租户管理能力，包括 API Key、用户、团队、组织管理；
- 提供预算、用量统计、审计日志等治理能力；
- 提供管理后台，支持可视化查看系统运行状态；
- 在此基础上扩展一个面向 Agent 场景的“社会沙盘生成与演练平台”，支持后端生成、状态推进和前端可视化展示。

---

## 4. 系统总体架构

本项目整体采用“Go 网关后端 + Next.js 管理前端”的双层架构，但从论文表达上，更应该强调它首先是一个**网关系统**，其次才是一个带管理台的应用系统。

“网关”的核心含义在于：

- 它位于上层 Agent 应用与下层异构模型资源之间；
- 它不直接等同于某个单一业务模块，而是承担统一入口职责；
- 它负责协议适配、请求转发、路由选择、访问控制、观测审计和治理约束；
- 它把原本分散在各个 Agent 应用中的模型接入逻辑上收为平台能力。

因此，本项目的关键设计思路不是“再做一个聊天后端”，而是：**在 Agent 系统与异构模型基础设施之间，构造一个统一、可治理、可扩展、可观测的中间层。**

### 4.1 后端网关层

后端采用 Go 实现，核心职责包括：

- 提供统一 OpenAI 兼容 API；
- 对接多种模型提供商；
- 根据策略进行请求路由；
- 执行限流、预算、审计、日志等治理逻辑；
- 暴露管理接口；
- 为 Agent 沙盘模块提供生成、查询和时间推进接口。

### 4.2 前端管理层

前端采用 Next.js 实现，核心职责包括：

- 提供仪表盘与管理台界面；
- 展示 API Key、用户、团队、组织、审计和全局用量信息；
- 提供 Agent Town 社会沙盘可视化页面；
- 通过同源代理/重写方式访问后端管理接口，降低跨域带来的开发复杂度。

### 4.3 关键模块关系

系统可以抽象为以下几个层次：

1. **模型接入层**：对接不同大模型供应商；
2. **协议适配层**：把底层差异收敛为统一接口；
3. **网关路由层**：统一接收请求并选择合适的模型后端；
4. **治理控制层**：实现认证、限流、预算、审计、追踪；
5. **管理展示层**：通过可视化页面展示运行状态和配置；
6. **Agent 场景扩展层**：在管理台中增加社会沙盘生成与时间推进能力。

从体系结构上看，本项目的“网关性”主要体现在三点：

- **统一入口**：上层应用只面向网关，而不面向具体厂商；
- **统一决策**：路由、预算、权限、审计等逻辑统一在网关中执行；
- **统一治理**：把异构模型资源纳入同一平台进行观测和控制。

## 5.2 异构模型统一接入

项目已支持以统一配置方式接入多种模型后端，并通过 provider 抽象隐藏差异。当前代码结构已经具备扩展以下异构提供方的能力：

- OpenAI
- Azure OpenAI
- Anthropic
- Google / Gemini
- 其他兼容 OpenAI 协议的模型服务

如果从毕设主题“异构网关”来理解，这里的“异构”不能只简单写成“支持多个厂商”，而应该进一步概括为三层含义：

### 第一层：模型来源异构

不同请求可以来自不同模型后端，它们在：

- 接口地址
- 认证方式
- 模型名称
- 性能特征
- 成本结构
- 限制条件

上都存在差异。网关通过 provider 配置与统一入口屏蔽这些差异，使上层 Agent 不需要针对每个供应商写多套调用逻辑。

### 第二层：能力选择异构

不同模型并不只是“来源不同”，还体现为能力分工不同。例如：

- 高质量推理模型适合复杂决策；
- 低成本模型适合批量调用；
- 嵌入模型适合检索；
- 响应速度更快的模型适合交互式 Agent；
- 某些模型适合语音、转写或 Responses API。

因此，异构网关的意义不只是“兼容”，更是把底层模型差异转化为可调度资源。

### 第三层：Agent 任务异构

在 Agent 系统中，不同 Agent 对模型的需求往往不同。例如：

- 规划 Agent 更关注推理深度；
- 检索 Agent 更关注嵌入与召回；
- 执行 Agent 更关注延迟和吞吐；
- 评估 Agent 更关注稳定性和一致性。

这意味着网关不仅面向“人类用户请求”，还要面向“多角色 Agent 请求”。因此，“异构”在本项目中最终体现为：**把不同模型能力、不同任务角色和不同租户约束，统一纳入一个可调度、可治理的中间层。**

这一点体现了“异构网关”的核心思想：**统一入口、统一协议、统一治理、底层多模型异构实现。**

## 5.8 路由 Memory 演化实验层（社会沙盘扩展）

这一部分不是本项目的主体，而是异构网关之上的一个拓展实验层。它的作用不是把论文主题转向“社会模拟系统”，而是为网关提供一个可演化、可观察、可沉淀的路由记忆（routing memory）生成环境。

### 5.8.1 模块定位

在传统模型网关基础上，本项目进一步增加了一个面向 Agent 场景的可视化演化模块，即“社会沙盘”。但在论文定位上，它更适合被描述为：**网关路由 memory 的实验层与数据沉淀层**。

其核心价值在于：

- 构造多角色、多状态、多约束的复杂交互环境；
- 用演化过程模拟不同请求、不同策略、不同后果之间的动态关系；
- 将日志、事件、行为轨迹和阶段结果沉淀为可回看的 memory；
- 为后续网关路由优化提供经验样本，而不仅仅是做一个可视化演示页面。

换句话说，社会沙盘在本项目中的定位应当是：**服务于异构网关策略演化的上层实验机制**。

### 5.8.2 当前已实现的后端接口

后端新增了三个核心接口：

- `POST /sandbox/generate`：根据提示词生成演化场景；
- `GET /sandbox/state`：获取指定演化场景状态；
- `POST /sandbox/step`：推进时间，更新 Agent 行为、日志与 memory。

### 5.8.3 当前状态数据

目前该实验层状态中已包含：

- `name`：场景名称
- `premise`：背景设定
- `theme`：主题类型
- `protocol`：治理协议
- `institutions`：制度/机构
- `rules`：规则
- `templates`：事件模板
- `archive`：历史沉淀信息
- `districts`：地图区域
- `agents`：Agent 列表
- `tick`：时间步
- `logs`：过程日志

其中 `logs` 与 `archive` 可以进一步抽象为路由策略演化中的观察记录与经验记忆。

### 5.8.4 当前实验层能力

前端 `Agent Town` 页面目前已经实现：

- 输入一段场景提示词；
- 点击“生成沙盘”；
- 通过后端返回的数据绘制 GUI 场景；
- 用蓝点表示移动中的 Agent；
- 点击 Agent 查看其当前行动；
- 点击“推进时间”后获取新的时间步状态；
- 展示日志、archive、基础配置等信息。

### 5.8.5 与异构网关主线的关系

如果从毕设主线看，这一模块最重要的意义不是“社会模拟”本身，而是：

- 它为路由策略提供可演化的实验空间；
- 它为网关决策提供可沉淀的历史记忆；
- 它为未来的自适应路由、记忆增强路由和 Agent 协同调度提供原型基础。

因此，本项目可以表述为：**以异构网关为主体，以社会沙盘作为路由 memory 演化拓展层。**

## 6. 本项目的技术特点与创新点

结合当前实现，本项目可提炼出以下几个技术特点：

### 6.1 统一协议屏蔽异构差异

通过统一 OpenAI 风格接口，将底层不同模型服务商的差异隐藏在网关内部，降低上层 Agent 系统接入复杂度。

### 6.2 以网关为中心的架构设计

本项目最重要的设计思路之一，是没有把系统做成“某个直接调用模型的业务后端”，而是把它设计为位于上层应用与下层模型资源之间的网关中间层。

这意味着项目重点放在：

- 统一入口；
- 请求分发；
- 路由决策；
- 访问控制；
- 配额与预算；
- 日志审计；
- 观测追踪；
- 与上层 Agent 系统解耦。

从论文角度来说，这种“中间层平台化”思路，比“直接封装若干模型调用接口”更能体现系统设计价值。

### 6.3 路由与治理一体化

不仅有模型转发能力，还同时整合了：

- 路由策略
- 配额与预算
- 多租户管理
- 审计日志
- 观测指标

相比普通转发层，具有更强的平台治理属性。

### 6.4 面向 Agent 场景的异构资源调度潜力

本项目并不只解决“多模型接入”问题，而是为后续 Agent 多角色协作提供一个统一调度底座。其潜在意义在于：

- 不同 Agent 可以请求不同模型；
- 不同任务可以匹配不同成本与时延特征的后端；
- 同一平台可以对多种 Agent 请求统一治理；
- 上层 Agent 编排逻辑与下层模型选择逻辑解耦。

这使得“异构网关”从单纯的模型兼容层，进一步上升为 Agent 基础设施。

### 6.5 面向路由 Memory 的扩展能力

项目没有停留在“模型网关”层面，而是在网关之上增加了一个面向 Agent 场景的演化实验层，用于沉淀日志、状态与历史轨迹，进一步形成可复用的 routing memory。这体现了系统从“静态路由网关”向“可演化网关”延伸的潜力。

### 6.6 前后端协同的可视化能力

通过 Go 后端 + Next.js 前端实现管理闭环，不仅可以对请求进行治理，还可以通过图形化界面直观展示 Agent 状态、日志与演练过程。

### 6.7 工程实现偏生产化

系统同时考虑了：

- 本地开发模式
- 独立部署模式
- 分布式模式
- 指标与日志
- 健康探测
- 配置加载

说明项目具备较强工程实践价值。

## 7. 当前实现仍存在的不足

在进入不足分析前，需要先明确一个论文表达上的关键判断：

## 6.8 为什么本项目可以被称为“Agent 异构网关”

本项目之所以不是普通的管理后台或模型调用服务，而可以被称为“Agent 异构网关”，主要基于以下判断：

### （1）它处在 Agent 与底层模型资源之间

上层系统并不直接调用具体厂商 API，而是统一通过网关访问模型能力。因此它承担的是“入口”和“中间层”角色，而不是某个具体业务功能模块。

### （2）它处理的是异构资源，而不是单一后端

网关面对的不是一个模型实例，而是多个不同来源、不同能力、不同成本、不同部署方式的模型资源池。系统的核心任务之一，就是把这些异构资源抽象为统一可调用能力。

### （3）它具备路由与治理决策能力

如果一个系统只是把请求原样转发给固定后端，那更像代理；而本项目支持：

- 多策略路由；
- 多租户约束；
- 预算与配额控制；
- 审计与追踪；
- 管理与观测。

这说明它不是简单代理，而是具备平台决策属性的网关。

### （4）它面向的是 Agent 应用场景

本项目不仅服务于普通文本调用，还试图作为 Agent 系统的基础设施底座。特别是在社会沙盘模块中，已经体现出“多个角色、多个状态、多个行动逻辑”的 Agent 场景扩展方向。后续如果将不同 Agent 路由到不同模型后端，其“Agent 异构网关”的定位会更加完整。

因此，更准确地说，本项目当前已经实现了一个：**面向 Agent 应用扩展的异构模型网关原型系统**。

## 6.9 大模型增强的异构网关流量调度设想

在传统网关中，流量调度通常依赖轮询、随机、最小时延、最低成本、最小负载等确定性策略。这些方法在工程上成熟有效，但更多属于对“当前状态”的被动响应，难以充分利用历史行为、任务语义和阶段性经验，因此在 Agent 场景下存在一定局限。

对于面向 Agent 的异构网关而言，请求并不是完全同质的。不同任务在时延敏感度、成本敏感度、模型能力要求、稳定性要求等方面存在明显差异；不同 provider 在性能波动、负载状态、限额约束和故障模式上也并不一致。因此，异构网关中的流量调度问题，本质上是一个同时受到实时状态、历史记忆和未来趋势影响的动态决策问题。

基于这一判断，本文提出在现有网关之上引入**大模型增强的流量调度机制**。其核心思想不是让大模型直接接管每一次在线流量分发，而是让大模型参与以下三个过程：

### 6.9.1 调度记忆归纳

将网关运行日志、路由结果、失败记录、成本变化、时延波动等信息沉淀为 routing memory，由大模型对这些历史信息进行语义归纳，形成“什么类型请求更适合什么路由策略”“什么情况下应降低某 provider 权重”“什么模式意味着即将出现拥塞或失败”的经验知识。

### 6.9.2 流量趋势预测

基于近期请求分布、provider 状态、预算压力和历史波动模式，大模型可作为预测增强模块，对下一阶段可能出现的高峰、拥塞、成本上升或失败风险进行提前判断，使网关调度从“被动响应”走向“前瞻调度”。

### 6.9.3 策略建议生成

在实时状态与历史 memory 的共同作用下，大模型可以输出调度建议，例如：

- 当前应优先采用 lowest-latency 还是 least-busy；
- 某类请求是否应临时偏向高质量模型；
- 某个 provider 是否应降低权重或进入观察期；
- 在预算压力增加时，是否应切换到更低成本策略。

但最终执行权仍应由网关中的确定性规则模块负责，以保证预算约束、限流、熔断、隔离与审计边界不被破坏。

### 6.9.4 混合调度架构

因此，较为合理的系统架构应当是：

- **实时执行层**：负责确定性路由、限流、预算、熔断和治理控制；
- **状态感知层**：负责采集日志、统计指标和运行状态，并沉淀 routing memory；
- **LLM 增强决策层**：负责经验归纳、趋势预测和策略建议生成。

这种架构可概括为：**规则兜底、memory 驱动、LLM 增强**。它既保留了传统网关的工程稳定性，又为面向 Agent 场景的自适应调度提供了可研究、可扩展的方向。

在本项目当前阶段，系统已经增加了一个可展示的“调度建议原型层”，能够结合运行状态与 routing memory 给出推荐策略、推荐 provider、风险提示和后续动作建议。尽管这一能力仍处于原型阶段，但它为后续实现真正的预测性、自适应流量调度提供了清晰的演进路径。

## 7. 当前实现仍存在的不足

作为毕设初稿，需要客观说明当前限制：

### 7.1 Agent 决策仍为 mock

当前社会沙盘中的 Agent 行为主要由后端预设状态机推进，还未将每个 Agent 的决策真正接入异构大模型调用链。

### 7.2 沙盘状态持久化仍可继续增强

当前沙盘状态主要保存在进程内存中，适合演示和原型验证，但在长期运行、多用户并发和系统重启恢复方面仍可继续改进。

### 7.3 沙盘编辑能力还可继续扩展

目前已支持生成、查看和推进，但对 institutions、rules、templates、agents 的在线编辑能力还可进一步完善为独立接口与表单。

### 7.4 Agent 协作逻辑仍较简化

当前系统已能展示多 Agent 移动和行为日志，但更复杂的协作、冲突、谈判、记忆演化和群体互动机制还可以继续深化。

## 8. 后续可继续开展的工作

本项目后续可以从以下几个方向继续扩展：

### 8.1 接入真实异构模型决策

将每个 Agent 的行动选择交由真实 LLM 完成，并通过网关动态路由到不同模型供应商，真正体现“Agent 异构网关”的核心能力。

### 8.2 增强社会沙盘状态持久化

将沙盘状态、日志、记忆、事件时间线持久化到数据库中，支持恢复与回放。

### 8.3 增加沙盘编辑与编排功能

支持用户在前端直接编辑：

- 区域布局
- 机构与制度
- 规则集
- 事件模板
- Agent 属性

### 8.4 引入多 Agent 协商与博弈机制

进一步增加：

- Agent 对话协商
- 冲突升级与缓解
- 资源争夺
- 联盟形成
- 集体情绪传播

### 8.5 构建可评估的实验体系

为不同路由策略、不同模型组合、不同 Agent 决策方式设计实验指标，例如：

- 响应时延
- Token 消耗
- 成本
- 稳定性
- 社会模拟合理性
- 任务完成率

## 9. 可作为论文中的阶段性结论

本项目已经实现了一个具备实际工程能力的 Agent 异构网关原型系统。系统以 Go 实现高性能统一网关，以 Next.js 构建管理与展示界面，在统一 OpenAI 协议、多模型路由、多租户治理、预算控制、审计追踪和可观测性方面形成了完整的基础设施能力。

在此基础上，项目进一步增加了一个面向 Agent 场景的演化实验层，用于生成并沉淀路由相关的日志、状态与 memory，为未来的自适应路由、记忆增强路由和多 Agent 协同调度提供原型基础。

当前版本已经具备：

- 可运行的异构网关能力；
- 可视化的管理后台；
- 面向路由 memory 的实验性拓展层；
- 可继续扩展为真实多 Agent 决策与自适应路由系统的架构基础。

因此，本项目不仅具有一定的理论研究价值，也具备较强的工程实践意义，可作为毕业设计论文与演示系统的核心成果基础。
