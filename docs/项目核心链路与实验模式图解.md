## 2. 平台六层概念图

这一层对应 gateway visualizer / simulation 里的概念视角，强调“平台是多层控制面”，不等价于实际函数调用顺序。

```mermaid
flowchart LR
    L1[请求接入层] --> L2[协议适配层]
    L2 --> L3[AI 流量调度层]
    L3 --> L4[请求执行层]
    L4 --> L5[治理控制层]
    L5 --> L6[观测优化层]

    L1n[接收 HTTP 请求或上层 Agent 请求]
    L2n[统一成 OpenAI 风格请求]
    L3n[根据策略 记忆 约束做路由与调度]
    L4n[真正调用底层 provider 或触发工具循环]
    L5n[预算 配额 审计 访问控制]
    L6n[把结果沉淀成 memory 指标与运行信号]

    L1 -.-> L1n
    L2 -.-> L2n
    L3 -.-> L3n
    L4 -.-> L4n
    L5 -.-> L5n
    L6 -.-> L6n
```

如果只问“真正哪一层在打模型”，答案是 `请求执行层`。如果问“哪一层决定为什么打这个模型”，答案主要在 `流量调度层`。

## 3. `control/conversation/chat` 实际核心链路

### 3.1 总体执行图

```mermaid
flowchart TD
    A[用户请求 /control/conversation/chat] --> B[解析消息与最后一条 user turn]
    B --> C[识别 intent]
    C --> D[buildRoutingProfile]
    D --> D1[推断 complexity]
    D --> D2[推断 required_tools]
    D --> D3[推断 required_capabilities]
    D --> D4[推断 latency_budget]

    D --> E{require_team and team_routing_enabled}
    E -->|yes| F[Team Routing]
    E -->|no| G[Agent Routing]

    F --> F1[选择 team]
    F1 --> F2[选择 lead agent]
    F2 --> H[得到 selected agent]

    G --> H

    H --> I{token or cost optimization enabled}
    I -->|yes| I1[压缩历史消息]
    I -->|yes| I2[重排候选模型顺序]
    I -->|yes| I3[按 required_tools 裁剪工具范围]
    I -->|no| J[保持原始请求]

    I1 --> K[resolve Tool Marketplace 绑定]
    I2 --> K
    I3 --> K
    J --> K

    K --> L[构造 gateway request]
    L --> M[候选模型调度]
    M --> N[LLM 请求与 MCP tool loop]
    N --> O[返回 assistant message]
    O --> P[记录 route memory]
    O --> Q{是否走了 team}
    Q -->|yes| R[记录 team memory]
    Q -->|no| S[结束]
    R --> S
```

### 3.2 路由决策优先级

`Agent Router` 不是单一路由器，而是一条有优先级的决策链。

```mermaid
flowchart TD
    A[RoutingProfile] --> B{显式指定 agent?}
    B -->|yes| B1[explicit-agent]
    B -->|no| C{低复杂度且 token fast path 命中?}
    C -->|yes| C1[token-fast-path -> general-orchestrator]
    C -->|no| D{score router 有结果?}
    D -->|yes| D1[score-router]
    D -->|no| E{LLM router fallback 有结果?}
    E -->|yes| E1[autonomous-router]
    E -->|no| F{高分 memory hit?}
    F -->|yes| F1[memory-hit]
    F -->|no| G[intent-router fallback]
```

### 3.3 Team Routing, Agent Routing, Candidate Scheduling 的关系

```mermaid
flowchart LR
    T[Team Routing] --> A[Agent Routing]
    A --> C[Candidate Model Scheduling]

    TM[Team Memory] --> T
    RM[Route Memory] --> A
    RU[候选模型使用历史 RPM TPM cooldown] --> C

    TT[团队工具覆盖] --> T
    AC[能力匹配 延迟适配 required_tools] --> A
    CS[passive greedy-current predictive] --> C
```

这三层不是并列的三套系统，而是逐层收缩执行路径：

- Team Routing 决定是否先进入一个 team，以及 lead agent 是谁。
- Agent Routing 决定单个 expert agent。
- Candidate Scheduling 决定该 agent 下面到底打哪个 provider/model。

### 3.4 关键评分信号

#### Team 评分

Team 选择大致依赖这四类信号：

- `teamBaseScore`
- capability match
- team memory weight
- tool coverage

可近似写成：

```text
team_score =
  0.30 * base +
  0.35 * capability_match +
  0.20 * team_memory +
  0.15 * tool_coverage
```

#### Agent 评分

单 agent 选择大致依赖：

- `agentBaseScore`
- capability match
- route memory weight
- latency fit
- 如果有 required tools，还会把 tool coverage 纳入评分

典型形式：

```text
agent_score =
  0.25 * base +
  0.35 * capability_match +
  0.20 * route_memory +
  0.20 * latency_fit
```

当请求声明了 `required_tools` 时，会退化成一版更看重 `tool_coverage` 的评分。

#### Candidate 调度策略

候选模型层有三种模式：

- `passive`
  - 基本保持声明顺序/权重顺序
  - 不主动根据预测饱和度预跳过候选
- `greedy-current`
  - 根据当前快照负载决策
  - 看当前时刻的 RPM/TPM 压力
- `predictive`
  - 根据短窗口预测来预判是否会饱和
  - 会提前跳过 `predicted_saturated` 的候选

## 4. 执行层与 MCP tool loop

真正容易出故障的地方不是前面的路由判定，而是后面的执行循环。

```mermaid
sequenceDiagram
    participant Router as Conversation Router
    participant Scheduler as Candidate Scheduler
    participant LLM as LLMux Client
    participant MCP as MCP Manager
    participant Provider as Provider Model
    participant Memory as Memory Stores

    Router->>Scheduler: rankCandidateModelsForProfile(agent, profile)
    loop 候选模型尝试
        Scheduler->>Provider: ChatCompletion(provider/model)
        Provider-->>Scheduler: response
        alt 返回 tool calls
            Scheduler->>MCP: ExecuteToolCalls
            MCP-->>Scheduler: tool results
            Scheduler->>Provider: 追加 tool results 后再次请求
        else 正常完成
            Scheduler-->>Router: selected candidate + final response
        else throttled
            Scheduler->>Scheduler: 标记 cooldown 并切下一个 candidate
        else failed
            Scheduler-->>Router: 失败
        end
    end
    Router->>Memory: persist route memory
    Router->>Memory: persist team memory if needed
```

可以把失败面分成两类：

- 候选模型层失败
  - unauthorized
  - predicted saturated
  - cooling down
  - provider error
- 工具循环层失败
  - `exceeded maximum tool iterations (N)`

当前真实实验里更突出的瓶颈是第二类，也就是工具循环过长。

## 5. `control/lab/compare` Value Lab 对照模式

### 5.1 Value Lab 总图

```mermaid
flowchart TD
    A[POST /control/lab/compare] --> B[normalizeConversationLabRequest]
    B --> C{scenario == memory-follow-up}
    C -->|yes| D[预先 seed route memory 与 team memory]
    C -->|no| E[不 seed memory]

    D --> F[并行执行 baseline 与 optimized]
    E --> F

    F --> G[baseline branch]
    F --> H[optimized branch]

    G --> G1{哪种 scenario}
    G1 -->|grounded-repo-qa| G2[plain chat baseline]
    G1 -->|speed-chat| G3[plain chat baseline]
    G1 -->|memory-follow-up| G4[routed baseline but memory_reuse_enabled=false]

    H --> H1[routed optimized]
    H1 --> H2[memory_reuse_enabled=true]
    H1 --> H3[可选 token or cost optimization]
    H1 --> H4[可选 tool injection]
    H1 --> H5[candidate scheduling]

    G2 --> I[比较 latency token cost quality]
    G3 --> I
    G4 --> I
    H2 --> I
    H3 --> I
    H4 --> I
    H5 --> I

    I --> J[输出 recommended_winner]
    I --> K[输出 winning_dimensions]
    I --> L[输出 value_summary]
```

### 5.2 Value Lab 三种场景模式

| 场景 | baseline 路径 | optimized 路径 | 主要想观察什么 |
| --- | --- | --- | --- |
| `grounded-repo-qa` | 直接 plain chat，不走复杂路由 | 走完整 routed chain，尽量少量但真实地使用文件工具 | groundedness、tool awareness、route depth |
| `speed-chat` | 直接 plain chat | 仍走优化链，但要求保持轻量 | 快速请求下优化链是否会过度设计 |
| `memory-follow-up` | 走 routed chain，但显式关闭 `memory_reuse_enabled` | 走 routed chain，并允许 memory reuse | 单独隔离记忆重用的价值 |

### 5.3 Value Lab 的关键实验开关

| 开关 | 含义 |
| --- | --- |
| `token_optimization` | 压缩上下文，限制输出预算，裁剪工具范围 |
| `cost_optimization` | 候选模型按更低成本路径重排 |
| `memory_reuse_enabled` | 是否允许 route memory / team memory 直接参与选路 |
| `team_routing_enabled` | 是否允许 team route |
| `candidate_strategy` | `passive` / `greedy-current` / `predictive` |
| `tool_injection_enabled` | 是否把 marketplace 工具真正注入到请求里 |
| `tool_scope_pruning_enabled` | 是否只保留 required tools 对应的工具摘要 |
| `max_tool_iterations` | MCP tool loop 上限 |

### 5.4 Value Lab 的 baseline 不是一直同一种 baseline

这一点很关键：

- 在 `grounded-repo-qa` 与 `speed-chat` 场景里，baseline 是 plain chat baseline。
- 在 `memory-follow-up` 场景里，baseline 不是 plain chat，而是“同一条 routed chain，但禁用 memory reuse”。

也就是说，Value Lab 里至少有两种 baseline 语义：

- `plain baseline`
- `routed baseline without memory reuse`

## 6. Agent Router 视角图

如果把 `control/conversation/chat` 看成一个 memory-enhanced multi-agent router，它的结构可以简化成下面这张图。

```mermaid
flowchart TD
    U[User Prompt] --> P[RoutingProfile]
    P --> M1[Route Memory 检索]
    P --> M2[Team Memory 检索]
    P --> T{需要 team 吗}

    T -->|yes| T1[选择 team]
    T1 --> T2[选择 lead agent]
    T2 --> A[选中 agent]

    T -->|no| A1[单 agent 评分路由]
    A1 --> A

    A --> C[候选模型排序与 failover]
    C --> X[执行]
    X --> Y[assistant response]
    Y --> Z1[route memory 强化]
    Y --> Z2[team memory 强化]
```

从真实实现看，`Agent Router` 的核心不是“让 LLM 随机想一个 agent”，而是把以下信号压进一套带回退顺序的决策链：

- intent
- complexity
- required tools
- required capabilities
- latency budget
- route memory
- team memory
- candidate health
- tenant/org scope

## 7. 实验模式地图

### 7.1 研究实验总图

```mermaid
flowchart TD
    A[scripts/experiments] --> B[Exp 2.1 记忆增强路由]
    A --> C[Exp 2.2 预测式调度]
    A --> D[Exp 2.3 工具增强]
    A --> E[Value Lab 真实对照]

    B --> B1[baseline-memoryless-routing]
    B --> B2[our-memory-augmented-routing]

    C --> C1[baseline-passive-fallback]
    C --> C2[baseline-greedy-current]
    C --> C3[our-predictive-scheduling]

    D --> D1[baseline-no-tools]
    D --> D2[our-tool-augmented]

    E --> E1[baseline]
    E --> E2[optimized]
```

### 7.2 实验组与开关的对应关系

| 实验 | 入口 | 对照组 | 主要开关 |
| --- | --- | --- | --- |
| Exp 2.1 | `/control/conversation/chat` | `baseline-memoryless-routing` vs `our-memory-augmented-routing` | 主要隔离 `memory_reuse_enabled=false/true` |
| Exp 2.2 | `/control/conversation/chat` | `baseline-passive-fallback` vs `baseline-greedy-current` vs `our-predictive-scheduling` | 主要隔离 `candidate_strategy=passive/greedy-current/predictive` |
| Exp 2.3 | `/control/conversation/chat` | `baseline-no-tools` vs `our-tool-augmented` | 主要隔离 `tool_injection_enabled`、`tool_scope_pruning_enabled`、`max_tool_iterations` |
| Value Lab | `/control/lab/compare` | `baseline` vs `optimized` | 质量收益与执行代价的真实对照 |

### 7.3 Exp 2.3 的特别之处

Exp 2.3 不是在比“谁更会路由”，而是在比“工具增强是否真的改变 agent 的执行能力边界”：

- baseline-no-tools
  - `memory_reuse_enabled=false`
  - `team_routing_enabled=false`
  - `tool_injection_enabled=false`
  - `tool_scope_pruning_enabled=false`
  - `max_tool_iterations=2`
- our-tool-augmented
  - `memory_reuse_enabled=false`
  - `team_routing_enabled=false`
  - `tool_injection_enabled=true`
  - `tool_scope_pruning_enabled=true`
  - `max_tool_iterations=6`

所以 Exp 2.3 的重点不在 memory，不在 team，而在工具能力是否真正进入执行链。

## 8. 一句话看懂当前系统

```mermaid
flowchart LR
    A[平台入口] --> B[RoutingProfile 构建]
    B --> C[Team 或 Agent 选路]
    C --> D[候选模型调度]
    D --> E[MCP 工具增强执行]
    E --> F[结果返回]
    F --> G[记忆沉淀与下次复用]
```

这条链路的当前工程现实可以概括成：

- 路由层已经明显成形。
- memory 已经真实参与选路。
- candidate scheduling 已经能做策略实验。
- tool augmentation 已经真实改变执行行为。
- 当前主要瓶颈在 tool loop 的迭代控制，而不是 router 完全选不准。
