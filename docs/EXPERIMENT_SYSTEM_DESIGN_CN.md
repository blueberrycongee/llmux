# LLMux 论文实验体系设计方案

## 1. 文档目标

本文档用于把论文中的核心价值主张转化为一套可以真正执行、复现、统计、汇报的实验体系。

这套实验体系的目标不是“补几个截图”或“跑几次接口”，而是系统性回答下面这个问题：

> LLMux 相比传统网关、无记忆路由、被动调度和无工具 Agent，究竟多带来了什么价值，这些价值能否被稳定地量化证明？

## 2. 论文核心价值主张回顾

你的论文当前有 5 个核心创新点：

1. 记忆增强的分层路由  
   Route Memory + Team Memory

2. 预测式调度算法  
   基于负载预测规避 RPM / TPM 限流碰撞

3. 工具增强 Expert Agent  
   通过 MCP 注入真实工具能力

4. 团队演练与经验沉淀  
   用 rehearsal + Team Memory 持续优化团队协作

5. 多约束多目标协同优化  
   在多个约束下同时优化成功率、限流碰撞、延迟、资源利用率

这些创新点决定了实验体系不能只做单一 benchmark，而必须分层设计。

## 3. 实验体系总览

建议把论文实验拆成 4 大类：

## 3.1 第一类：基础网关层实验

目标：证明 Go 网关底座本身具备高性能、低开销、低尾延迟优势。

已知现状：

- 这一层已有数据。
- 主要是 LLMux vs LiteLLM 的高并发性能对比。

价值：

- 证明基础框架优势。
- 但不能直接证明分层路由、记忆机制、预测调度等核心创新的价值。

## 3.2 第二类：核心创新验证实验

目标：逐一验证 5 个核心创新是否真的带来可测收益。

建议至少覆盖：

- Exp 2.1：记忆增强路由
- Exp 2.2：预测式调度
- Exp 2.3：工具增强 Agent
- Exp 2.4：团队演练与经验沉淀
- Exp 2.5：多约束多目标协同优化

这是论文最关键的实验层。

## 3.3 第三类：实际部署验证实验

目标：证明方法在持续运行和高并发压力下仍然稳定，而不是“只能在短时间 demo 中成立”。

建议覆盖：

- Exp 3.1：长期稳定性测试
- Exp 3.2：并发压力测试

## 3.4 第四类：对标研究

目标：回答“你的系统在学术和工程上相对现有主流方案处于什么位置”。

建议覆盖：

- Exp 4.1：与 LiteLLM、LangChain Router、手工规则路由对比

### 4.2.2 Value Lab：优化链路收益已经可以被实测观察到

当前已经对 `grounded-repo-qa` 场景做了 10 次真实对照实验。

关键结果：

- `optimized` 被推荐为 winner：8 / 10
- `baseline` 成功：10 / 10
- `optimized` 成功：8 / 10
- `baseline` 平均 latency：12183.30 ms
- `optimized` 平均 latency：39070.90 ms
- `optimized` 平均 tool calls：5.80

更关键的是，对“收益项”与“代价项”拆开后，可以清晰看到优化链路的价值：

#### 收益项

- Groundedness：`0.34 -> 0.81`，提升约 `138%`
- Hallucination Risk：`0.62 -> 0.2975`，下降约 `52%`
- Response Chars：`491.8 -> 927.75`，提升约 `88.6%`
- Route Depth：`1 -> 5`
- `tool-aware` 和 `agent-selection` 在 `winning_dimensions` 中均出现 `10` 次

#### 代价项

- Latency：上升约 `216%`
- Tokens：上升约 `1778%`
- Cost：上升约 `547%`

#### 结论

这组数据已经足以支持一个非常重要的论文论点：

- 当前优化链路的价值是真实存在的
- 但它的价值不是“更便宜”或“更快”
- 而是“更好的 Agent 选择、更强的工具感知、更高 groundedness、更低 hallucination risk”

也就是说，Value Lab 这一组实验已经能够证明：

- 优化链路是“高质量、高执行能力路径”
- 而不是“低成本、低时延路径”

#### 当前暴露的问题

optimized 的 2 次失败原因完全一致：

- `exceeded maximum tool iterations (10)`

这说明当前真实系统中，优化链路最大的工程问题不是“路由失效”，而是：

- 工具增强链过长时容易触达 MCP tool loop 上限

### 4.2.3 Agent Router：路由层已经表现出稳定性，但执行层瓶颈明显

当前已经对 `control/conversation/chat` 做了 10 次真实调用。

关键结果：

- 业务成功：6 / 10
- 平均客户端时延：41720.40 ms
- Selected Agent：`code-specialist`，10 次全命中
- Route Source：`score-router`，10 次全命中
- Memory Influence：`reused`，10 次全命中
- 成功样本中 Selected Candidate：全部为 `deepseek-primary/deepseek-chat`

#### 这组结果说明了什么

1. 路由层是稳定的  
   Agent 选择、Route Source 和 Memory Influence 基本没有抖动。

2. Route Memory 已经真实参与了路由  
   因为 `memory_influence = reused` 在 10 次里全命中。

3. 当前主要瓶颈不在“路由选错”，而在“工具循环失控”  
   4 次失败全部是：
   `exceeded maximum tool iterations (10)`

#### 结论

这组实验当前最有价值的地方，不是用来做“baseline vs optimized 收益对比”，而是用来证明：

- 你的优化链路在真实请求中已经稳定生效
- 路由层本身不是当前失败主因
- 真正需要继续优化的是工具增强执行层

### 4.2.4 Exp 2.3：工具增强机制已经能打出对照收益

当前已经基于 5 个默认任务做了一轮工具增强对照实验，任务主要围绕：

- 仓库目录识别
- MCP 实现定位
- 候选策略识别
- 实验脚本识别
- 报告文件识别

实验采用两组：

- Baseline：无工具 Agent
- Our Method：工具增强 Agent

#### 当前结果

| 指标 | 无工具基线 | 工具增强链路 | 结论 |
| --- | ---: | ---: | --- |
| API 成功率 | 100% | 60% | 工具增强引入了执行复杂度 |
| 语义成功率 | 40% | 60% | 工具增强对任务完成质量有提升 |
| 关键词覆盖均值 | 0.40 | 0.60 | 工具增强更容易命中真实仓库事实 |
| 平均 Tool Calls | 0.00 | 5.20 | 工具增强链路真实触发了 MCP 工具 |
| Tool 使用率 | 0% | 100% | 工具增强不是“假装有工具”，而是真实调用 |

#### 这组结果说明了什么

这组实验已经证明：

- 工具增强机制确实会改变 Agent 的执行行为
- 工具增强链路确实提升了语义成功率和事实命中率
- 工具增强带来的收益主要体现在“更能做”，而不是“更稳”

#### 当前局限

目前这组默认任务集主要使用：

- filesystem 工具

因此它能证明“工具增强机制有效”，但还不能充分覆盖：

- 数据库类工具
- 浏览器自动化
- 跨工具协作

另外，这组实验中增强链路仍然有 `max_iterations_hit_count = 2`，
说明 Exp 2.3 现在已经能产出证据，但还不是最终版本的数据集。

### 4.2.5 当前已经可以下的论文判断

基于目前已经跑出的真实数据，论文里已经可以较有把握地写出以下判断：

1. Go 网关底座性能优势已被现有 Benchmark 支撑。  
2. 优化链路的价值已经能在真实 Value Lab 对照里被观察到。  
3. 这种价值主要体现在质量与执行能力，而不是成本与时延。  
4. Agent Router 的路由稳定性已经在真实实验中体现出来。  
5. 当前最主要的工程瓶颈不是路由层，而是工具增强执行链的 tool loop 控制。  
6. 工具增强机制已经通过 Exp 2.3 的小规模对照显示出正向收益，但还需要更强任务集进一步放大证据力度。  

这些结论意味着：

- 论文已经不再是“纯概念方案”
- 但还没有达到“所有核心创新都完成系统性量化验证”的程度

## 5. 实验总原则

为了让论文说服力足够强，所有实验必须统一遵守以下原则：

### 5.1 基线明确

每个实验都必须有明确对照组，不能只跑“我们的优化链路”。

### 5.2 控制变量

同一实验中：

- 请求数据集一致
- 模型池一致
- 工具集一致
- 并发等级一致
- 限流配置一致
- 环境配置一致

否则无法归因。

### 5.3 指标一致

所有实验必须复用统一指标定义，避免不同章节口径不一致。

### 5.4 原始数据可追溯

每次实验必须落：

- 原始请求
- 原始响应
- 路由结果
- 模型选择
- 工具调用记录
- 统计摘要

### 5.5 结果区分三类

必须严格区分：

- 已测真实结果
- 目标值 / 预期值
- 理论推断

论文里绝不能把“预期数字”写成“实验结果”。

## 6. 核心指标定义

建议统一采用下面 6 个一级指标。

### 6.1 请求执行成功率

```text
成功率 = 成功执行的请求数 / 总请求数 × 100%
```

### 6.2 限流碰撞概率

```text
限流碰撞概率 = 发生限流碰撞的请求数 / 总请求数 × 100%
```

### 6.3 平均响应延迟

```text
平均响应延迟 = Σ响应延迟 / 成功执行请求数
```

单位：ms

### 6.4 模型资源利用率

```text
模型资源利用率 = Σ(Used_RPM / RPM_limit) / 模型数量 × 100%
```

如需更完整，可以同时计算 TPM 利用率，并分别报告 RPM / TPM 两个利用率。

### 6.5 记忆命中率

```text
记忆命中率 = 复用历史记忆的请求数 / 总请求数 × 100%
```

建议拆成：

- Route Memory 命中率
- Team Memory 命中率

### 6.6 路由一致性

```text
路由一致性 = 同类语义请求选中相同 Agent 的次数 / 同类请求总数 × 100%
```

其中“同类语义请求”必须通过人工标注或语义聚类先定义好。

## 8. 数据集设计

## 8.1 通用请求数据集

需要构造一个标准请求集，至少包含：

- 简单问答类
- 代码分析类
- 研究分析类
- 需要工具的复杂任务
- 需要多 Agent 协作的复杂任务

建议规模：

- 最小可用：1000 条
- 正式实验：3000 到 5000 条

## 8.2 语义同类请求簇

用于测试记忆命中率和路由一致性。

要求：

- 每个簇 5 到 20 条相似请求
- 同簇请求语义接近，但表达不同
- 为每个簇标注“理想 Agent / 理想 Team / 是否需要工具”

## 8.3 复杂任务集

用于工具增强和团队协作实验。

建议至少覆盖：

1. 代码查询 + 执行类
2. 数据查询 + 分析类
3. 信息检索 + 综合类
4. 多步骤自动化类
5. 跨工具协调类

## 8.4 长期流量回放集

用于长期稳定性和并发压力实验。

要求：

- 尽可能模拟生产请求分布
- 包含高峰 / 平峰 / 低峰
- 包含冷启动与热启动混合场景

## 9. 核心创新验证实验设计

## 9.1 Exp 2.1：记忆增强路由的有效性

### 核心问题

Route Memory 和 Team Memory 是否真的提升了路由质量与效率？

### 对照设计

#### Baseline 1：无记忆分层路由

- 不使用 Route Memory
- 不使用 Team Memory
- 每次请求从零开始决策
- 仅依赖语义匹配 + Agent / Team 评分

#### Our Method：融合记忆的分层路由

- 开启 Route Memory
- 开启 Team Memory
- 允许 consult / reuse 历史经验

### 指标

- 记忆命中率
- 路由决策时间
- 路由一致性
- 请求成功率
- 复用率

### 预期结论

如果实验成立，应能证明：

- 记忆机制显著提升了路由效率
- 同类请求的路由决策更稳定
- 成功率存在可测改善

### 当前可行性判断

这组实验当前最容易落地，因为仓库已经有：

- Route Memory
- Team Memory
- `conversation/chat`
- `value-lab`

缺的是显式 baseline 开关与标准化语义请求簇数据集。

## 9.2 Exp 2.2：预测式调度 vs 被动调度

### 核心问题

预测式调度是否真的能显著降低限流碰撞，并提高成功率？

### 对照设计

#### Baseline 2：被动调度

- 轮询或随机分配
- 限流发生后才 fallback

#### Baseline 3：当前负载贪心调度

- 只看当前 RPM / TPM 快照
- 总是选当前最低负载模型
- 不做未来 60 秒预测

#### Our Method：预测式调度

- 对未来窗口做移动平均预测
- 按安全边际排序
- 动态权重综合评分

### 指标

- 限流碰撞概率
- 请求成功率
- 平均延迟
- RPM / TPM 资源利用率

### 预期结论

如果实验成立，应能证明：

- 预测式调度不是只让成功率变高
- 它还能在低碰撞、低延迟和高利用率之间取得更好的协同

### 当前可行性判断

这组实验能做，但前提是必须先构造多模型、多限流配置环境。

最少需要：

- 5 到 8 个异构模型配置
- 明确的 RPM / TPM 限额
- 可控流量生成器

如果暂时没有足够真实模型，可以先用受控 mock limiter 做第一轮。

## 9.3 Exp 2.3：工具增强机制的贡献

### 核心问题

MCP 工具增强是否显著扩展了 Agent 的真实任务完成能力？

### 对照设计

#### Baseline 4：无工具 Agent

- 仅有 system prompt 能力定义
- 不可调用外部工具

#### Our Method：工具增强 Agent

- 注入 MCP 工具
- 可调用文件系统、数据库、网页抓取、代码执行等能力

### 测试任务类型

1. 代码查询 + 执行
2. 数据查询 + 分析
3. 信息检索 + 综合
4. 多步骤自动化
5. 跨工具协调

### 指标

- 任务成功率
- 信息准确性评分
- 信息完整性评分
- 工具调用次数
- 工具调用成功率
- 平均响应延迟

### 预期结论

如果实验成立，应能证明：

- 工具增强显著提高复杂任务成功率
- 工具增强带来的不是“更会说”，而是“更能做”

### 当前可行性判断

这组实验可以做，但要求工具环境稳定。

当前最少应保证：

- filesystem MCP 可用
- fetch MCP 可用
- 最好有数据库或代码执行类工具

同时，需要人工标注任务结果质量，不然“准确性 / 完整性”很难量化。

## 9.4 Exp 2.4：团队演练与经验沉淀的作用

### 核心问题

Team Memory 是否真的能优化团队协作效率与稳定性？

### 对照设计

#### Baseline 5：无演练机制

- 无 rehearsal
- 无 Team Memory 复用
- 团队协作完全由即时决策驱动

#### Our Method：有演练与经验沉淀

- 定期 rehearsal
- 团队结果沉淀为 Team Memory
- 相似任务复用历史团队组合与任务分工

### 测试场景

- 智能研发任务
- 智能办公任务
- 跨域协作任务

### 指标

- 团队协作成功率
- 平均完成时间
- 协作效率
- Agent 间通信开销
- 工具调用序列稳定性
- Team Memory 复用率

### 预期结论

如果实验成立，应能证明：

- 演练机制不是虚拟教学活动
- 它能够真实降低协作开销并提高成功率

### 当前可行性判断

这组实验可做，但要先补一类能力：

- 团队协作任务数据集
- 团队执行轨迹采集
- Agent 间通信或步骤日志的显式记录

如果当前系统日志里还没有结构化“协作步骤”字段，建议先补埋点。

## 9.5 Exp 2.5：多约束多目标协同优化

### 核心问题

你的方法是否真的实现了多目标协同，而不是“顾此失彼”？

### 对照设计

建议用 5 组方案做逐级对比：

#### Baseline 1：随机路由

- 无优化目标
- 随机分发

#### Baseline 2：单目标优化（只优化成功率）

- 只选历史成功率最高链路
- 忽视延迟、碰撞和利用率

#### Baseline 3：单目标优化（只优化延迟）

- 只选最小时延链路
- 忽视成功率、碰撞和利用率

#### Baseline 4：静态线性多目标

- 固定加权线性组合
- 权重不动态变化

#### Our Method：动态多目标协同

- 在约束条件下动态调权
- 基于预测做综合调度

### 指标矩阵

- 成功率
- 限流碰撞
- 平均延迟
- 资源利用率

### 评价方法

建议增加：

- Pareto 前沿分析
- 综合收益评分
- 各方案在不同约束场景下的鲁棒性分析

### 预期结论

如果实验成立，应能证明：

- 你的方法不是只在单个指标上取巧
- 而是在多目标约束下接近 Pareto 最优

### 当前可行性判断

这是论文最有说服力的实验之一，但也是最难做的。

前提条件包括：

- 多个 baseline 真正实现
- 指标可统一采样
- 负载环境受控

建议放在第二阶段后半段做。

## 10. 实际部署验证实验设计

## 10.1 Exp 3.1：长期稳定性测试

### 核心问题

系统在持续运行中是否稳定，是否存在性能衰减、内存泄漏或异常模式？

### 设计

- 持续运行 7 天
- 每小时采样一次核心指标
- 记录：
  - 成功率
  - 记忆命中率
  - 平均延迟
  - 内存使用量
  - 工具调用失败率
  - 限流碰撞率

### 分析方法

- 时间序列趋势分析
- 滑动窗口均值
- 波动率统计
- 异常点检测

### 成功判据建议

- 成功率波动标准差 < 5%
- 无持续上升的内存泄漏趋势
- 记忆命中率前期上升、后期稳定

### 当前可行性判断

可做，但必须有：

- 持续流量回放能力
- 周期采样任务
- 持久化日志与监控系统

## 10.2 Exp 3.2：并发压力测试

### 核心问题

系统在不同并发等级下性能如何衰减，是否出现崩溃临界点？

### 设计

建议做阶梯式压力测试：

- 50 QPS
- 100 QPS
- 150 QPS
- 200 QPS
- 250 QPS

每个等级运行 30 分钟。

### 指标

- 成功率
- 限流碰撞率
- 平均延迟
- P95 / P99
- 资源利用率
- 系统错误率

### 评价重点

- 是否平缓退化
- 是否存在突变崩溃点
- 是否出现特定工具链或特定模型链先失稳

### 当前可行性判断

可做，但建议在核心创新实验跑通后再做，否则很容易把基础 bug 与性能问题混在一起。

## 14. 这套实验体系能不能做好

答案是：能做，而且值得做，但必须按“实验工程”来推进，而不是按“写论文补图”来推进。

真正的关键不在于实验想法是否充分，而在于下面三件事是否落地：

1. baseline 开关是否真的做出来
2. 数据集是否真的标准化
3. 原始数据与统计链路是否真的自动化

如果这三件事补齐，这套实验体系会把论文从：

- “有想法的系统原型”

升级成：

- “关键创新已被系统性验证的完整方案”

如果现在就开始推进，建议按下面顺序做：
